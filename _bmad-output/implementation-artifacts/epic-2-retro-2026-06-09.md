## 3. What Went Well

1. **Boring-technology reuse paid off.** Every field type extended an existing base (`NumberFieldType`, `TextField`, `ReadOnlyFieldType`) via Django MTI. Zero new user-table columns, inherited numeric sort/filter for free (Currency, Percent), and a consistent frontend `FieldXSubForm.vue` + `fieldTypes.js` registration pattern. This is exactly the "favor boring tech" architecture bet validated.

2. **Cross-story intelligence carried forward.** Stories 2.2 and 2.3 each contain a "Previous Story Intelligence" section that explicitly reused the 2.1 CurrencyField playbook (subform delegation, plugin.js single-register, ruff alphabetical import order). Velocity and consistency improved story over story.

3. **Adopt-and-verify was a high-leverage win.** Story 2.4 (Autonumber) discovered the capability already existed upstream in Baserow. The team wrote **no new production code** — only verification tests (6 frontend unit + 3 E2E) mapped to ACs. Right call, fast close.

4. **Adversarial review earned its keep.** Review caught a CRITICAL (2.5) and a HIGH (2.1) that all unit tests had passed over. The "different reviewer, fresh context" discipline is working as designed.

5. **Defensive enforcement over UX trust.** Percent (2.2) hard-locks `number_suffix="%"` / `number_prefix=""` in `prepare_values()` regardless of API input; Barcode (2.3) wraps JsBarcode in try/catch for invalid Code128 chars. Inputs are not trusted — good instinct for a field layer.

## 4. Challenges & Growth Areas

1. **Hook-vs-signal selection bug (CRITICAL, Story 2.5).** Running Count relied on the `after_rows_created` *FieldType hook*, which fires **only** on the batch `force_create_rows` path. The single-row create path (the `create_row` REST endpoint + grid "add row" button — the *primary* user flow) never fired it, so counts went stale silently. The unit test masked it by exercising the batch path directly. **Root cause:** recompute logic was wired to a hook that doesn't cover the main user flow, and the test validated the wrong path. **Fix:** moved to a `rows_created` signal (fires on both paths) + added a single-row regression guard. This is now project memory (`after-rows-created-batch-only`).

2. **Signal handlers garbage-collected without `weak=False` (Story 2.5, twice).** Handlers nested inside `DatabaseConfig.ready()` are weakly referenced by Django's `Signal.connect()` default and get GC'd once `ready()` returns. Hit on both `rows_deleted` (during dev) and again conceptually on `rows_created` (during the AC#2 fix). **Lesson:** any signal handler connected from `ready()` MUST pass `weak=False`.

3. **Recurring migration churn — spurious `formview.mode` AlterField.** Migrations 0216, 0217, 0218, 0219 each bundle an unrelated `AlterField` on `formview.mode` from Django's lazy-choices serialization. Accepted four times in a row. Harmless (no schema/behavior change) but noisy, and "accepted as documented" in four separate reviews is a smell worth a one-time root-cause.

4. **Repeated review hygiene findings — File List drift & stale test counts.** Reviews of 2.1, 2.2, and 2.4 all flagged the same class of issue: QA-session files left uncommitted, File List missing the E2E spec, completion notes citing stale test counts. Auto-fixed each time, but it recurred across the majority of stories — a checklist gap, not a one-off.

5. **`toHumanReadableString` edge-case gaps.** Reviews of 2.3 and 2.4 found frontend tests covered `null`/`undefined` but not empty-string `''`. Recurring frontend test-coverage blind spot for read-only display fields.

6. **i18n key-location ambiguity.** Story 2.5 spec named `fieldType.runningCountDescription` in `modules/database/locales/en.json`; repo convention is `fieldType.<type>` + `fieldDocs.<type>` in `web-frontend/locales/en.json`. Dev deviated correctly, but the story text was wrong — story authoring didn't match repo reality.

---

## 5. Key Insights

1. **Test the primary user flow, not the convenient one.** The 2.5 CRITICAL existed because the test drove the batch path while users drive the single-row path. Per-field recompute work in Epic 3+ (drag-reschedule, dependency cascades) must be tested through the *user-facing* mutation path.
2. **`ready()` + signals = `weak=False`, always.** Now a hard rule.
3. **Adopt-and-verify before build.** 2.4 saved an entire implementation by checking upstream first. Make "does Baserow already do this?" a standard first step.
4. **MTI + base-type extension is the proven field-type recipe.** Reuse it; it's fast and low-risk.
5. **Adversarial review catches what unit tests mask.** Keep it mandatory; it found both real defects this epic.

## 7. Next Epic Preview — Epic 3: Visualize Data Multiple Ways

**Scope:** 14 stories. Kanban, Calendar, Timeline, Gantt (task dependencies + CPM critical path + milestones), and Map views. Realizes UJ-1, UJ-2, UJ-5. All views honor Epic 1's field-permission layer.

### Dependencies on completed work

- **Epic 1 field-permission layer** — every Epic 3 view must honor it. Epic 2 field types must render correctly inside the new views.
- **Row create/delete/update signal plumbing** — the same `rows_created` / `rows_deleted` / row-update signals hardened in Epic 2 (Story 2.5) are exactly what drag-reschedule and dependency-cascade flows will hook into.

### 🚨 Significant discoveries that affect Epic 3

1. **Bucket shift: A vs B.** Epic 2 was entirely Bucket B (license-clean, **no clean-room gate**). Epic 3's Kanban/Calendar/Timeline are **Bucket A — gated on the clean-room process** (Story 1.1). Gantt/Map are Bucket B. The team has no Epic-2 muscle memory for the clean-room workflow. **Impact:** the clean-room gate must be re-onboarded before Bucket A stories start, or they will stall at review.
2. **Infrastructure leap.** Epic 2 was "extend an existing field base class." Epic 3 introduces net-new infrastructure: geocoding provider abstraction + throttled queue (AR-6), TaskDependency/CPM backend engine (AR-8), and lazy-loaded Frappe Gantt / MapLibre renderers (AR-4/AR-5). This is a fundamentally larger surface — the field-extension recipe does not transfer.
3. **Mutation-path testing risk is higher.** Drag-to-reschedule and dependency cascades mutate rows through interactive flows. The exact failure mode from Story 2.5 (hook fires on wrong path, test masks it) is a live risk for every reschedule story.

**Epic update required before Epic 3 kickoff:** Recommend a short Epic 3 readiness review — confirm clean-room gate re-onboarding for Bucket A stories and a spike on the CPM/geocoding infra before committing story estimates.

## 10. Closure — Key Takeaways

1. **Reuse won.** MTI + base-type extension delivered 5 field types fast with zero new columns and zero incidents.
2. **Review caught what tests missed.** The 2.5 CRITICAL and 2.1 HIGH justify mandatory adversarial review permanently.
3. **Test the user's path.** The single biggest lesson — wire side effects to signals that cover the real flow, and test that flow.
4. **Epic 3 is a different game.** Bucket A clean-room gate + net-new infra (geocoding, CPM, lazy renderers). Do a readiness review before kickoff.
